# 第三批性能实测：2026-11-03

第三批已实现独立调度器、结构化反馈、稳定主图节点 ID、有状态分区与阶段轮转、
当前版本的最终覆盖，以及策略开关和 schema 4 报告。默认仍为 `legacy`，

本批有缩减质量改善，也有预算内质量和运行成本退化，尚不支持切换默认值。

## 跨区域和非单调条件

跨区域条件要求同时保留原始索引 `size//4` 与 `3*size//4` 的节点。
规模 128、检查预算 100 时，两者都得到 `(2, 182, 1, 3, 0)`：
判定 79 → 44 次，克隆 87 → 56 次，耗时中位数 190.18 → 142.53 ms。
1 秒预算下也得到同样成本并完成固定点覆盖。

非单调条件默认只接受节点数 `size`、`size//2+1`、`size//4`。
删除区域失败不意味着保留区域也会失败；这正是新增方向能改善质量的场景。

| 规模与预算 | legacy 最终成本 | stateful 最终成本 | 停止原因 legacy / stateful |
| --- | --- | --- | --- |
| 32，100 次检查 | `(32, 1457, 1, 1, 0)` | `(8, 404, 1, 2, 0)` | fixed_point / fixed_point |
| 128，100 次检查 | `(128, 5982, 1, 1, 0)` | `(32, 1499, 1, 2, 0)` | budget_exhausted / budget_exhausted |
| 128，1 秒 | `(128, 5982, 1, 1, 0)` | `(32, 1499, 1, 2, 0)` | budget_exhausted / fixed_point |
| 128，600 次检查 | `(128, 5982, 1, 1, 0)` | `(32, 1499, 1, 2, 0)` | fixed_point / fixed_point |

规模 128、600 次检查时，判定 256 → 129 次，耗时中位数 1.307 → 0.298 s。
stateful 的最终覆盖有 125 个尝试，全部由确定性缓存复用，约 19.6 ms；
覆盖仍有调度、证据和缓存查询成本，不能视为零开销。

```bash
../1012/.venv/bin/python benchmarks/reduction.py \
  --case chain --size 128 --condition non-monotonic \
  --repeat 3 --budget both --candidate-budget 600 --time-budget 5 \
  --compare-schedulers
```

原始记录：`batch3-matrix/cross-region-128/`、`non-monotonic-32/`、
`non-monotonic-128/`、`larger-budget/`。

## 保留的退化样本

### 四次判定预算下成本变大

32 节点链图、Relu 位于中间、缓存开启、检查预算 4，三次结果一致：

| 策略 | 最终成本 | 实际判定（含首尾） | 停止原因 |
| --- | --- | ---: | --- |
| legacy | `(8, 395, 1, 2, 0)` | 6 | budget_exhausted |
| stateful | `(8, 412, 1, 3, 0)` | 6 | budget_exhausted |

stateful 延续节点阶段，预算耗尽时保留更多尚未清理的图输入，字节成本增加 17。
这是完整成本的质量退化，不能因为节点数相同而记为持平。1 秒预算下两者都能缩到
`(1, 107, 1, 2, 0)` 并完成覆盖。

```bash
../1012/.venv/bin/python benchmarks/reduction.py \
  --case chain --size 32 --repeat 3 --budget calls \
  --candidate-budget 4 --compare-schedulers
```

### 规模阈值的覆盖成本增加

128 节点链图，节点数至少为 32 才复现。检查预算 100 时，两者都得到
`(32, 1614, 1, 1, 0)`；legacy 用 68 次实际判定完成固定点，stateful 达到
102 次（100 次候选加首尾）时停止，最小性为 `unproven`。

1 秒预算下两者均完成覆盖，但 stateful 需要 133 次实际判定，耗时 304.80 ms；
legacy 为 68 次、166.89 ms。保留方向在这一条件下增加了大量失败尝试。

### 续用尺度导致较晚发现有效粗块

16 节点链图，只允许节点数 16、12、6 复现。两者最终均为 `(6, 307, 1, 1, 0)`。
stateful 接受到 12 节点后延续尺度 4，随后细分；最终覆盖的标准尺度 6 才找到下一次接受。
当前版本覆盖因此必须失效并重新开始。

检查预算 100 的中位数：legacy 为 16 次判定、26.70 ms；stateful 为 75 次、131.70 ms。
这同时证明最终覆盖不可省略，以及保留有效尺度可能带来明显成本退化。

```bash
../1012/.venv/bin/python benchmarks/reduction.py \
  --case chain --size 16 --condition non-monotonic --interesting-sizes 16,12,6 \
  --repeat 3 --budget calls --candidate-budget 100 --compare-schedulers
```

三类退化的完整参数、源码 SHA-256、三次候选轨迹摘要与运行目录保存在
[证据摘要](performance-batch3-evidence.json) 的 `regressions`；原始批次分别为
`batch3-matrix/tight-calls/`、`threshold-128/`、`cover-accept/`。

## 轮转额度对照

另用新进程将内部 `StatefulScheduler.phase_quantum` 设为 1、4、8，每项三次，共 27 次。
未增加公开 CLI 参数；探针源码、SHA-256、完整参数及报告保留在
`output/performance/batch3-quantum/`，汇总见证据摘要的 `quantum_probe`。

| 条件 | 额度 1 | 额度 4 | 额度 8 |
| --- | --- | --- | --- |
| 32 节点，4 次检查 | `(16, 685, 1, 1, 0)` | `(8, 412, 1, 3, 0)` | `(8, 412, 1, 3, 0)` |
| 阈值 32，100 次检查 | 32 节点，未完成覆盖 | 32 节点，未完成覆盖 | 32 节点，未完成覆盖 |
| 允许 16、12、6 节点 | 65 次判定 | 68 次判定 | 75 次判定 |

减小额度能改善部分成本，却使紧预算下节点质量进一步下降，也没有解决阈值条件的额外判定。
当前保持内部额度 8 和 legacy 默认，后续应分别研究方向排序、尺度恢复及清理阶段时机，
以相同样本验证，避免只为单一退化条件调参。
