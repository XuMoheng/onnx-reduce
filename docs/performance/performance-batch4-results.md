# 第四批性能实测：2026-11-03

已实现实验性 `staged` 分阶段搜索、fast/complete 目标、独立 Finalizer、跨运行目标身份恢复，
以及实际输出文件的读回校验。默认继续使用 `legacy`；完整规则见[第四批设计](../design/staged-search-design.md)。

本批修复了紧预算样本的字节成本退化，并降低 16/12/6 样本相对于 stateful 的重复搜索成本；
常规样本仍有额外开销，规模阈值场景仍未解决。不支持据此切换默认策略。

## 方法与证据

基线为 `perf/reduction-strategy` 的 `4ac3835`。所有新策略对照都使用同一份当前源码，
共享清理、缓存、校验、接受规则和最终读回复检，只切换调度策略/运行目标。
旧策略修改前后另保存 60 组有序候选、调度轨迹、完整成本、内容摘要、计数、停止原因和
最小性对照；legacy 和 stateful 均完全一致。

使用相邻 `../1012/.venv/bin/python` 加载当前源码，不修改相邻项目。
每项三次、新进程、新运行目录，交替策略及采集开关顺序，不并发采样。
共 **468 次**，分为：

| 批次 | 配置 | 次数 |
| --- | --- | ---: |
| five-128 | 五类输入，128，调用 100 / 时间 1 秒，四种策略，采集开关 | 240 |
| five-512 | 五类输入，512，调用 100，四种策略，开启采集 | 60 |
| tight-calls | 链图 32，调用 4，四种策略，采集开关 | 24 |
| threshold-128 | 至少 32 个节点才复现，调用 100，四种策略，采集开关 | 24 |
| cover-accept | 允许 16/12/6 个节点，调用 100，四种策略，采集开关 | 24 |
| cross-region | 同时保留两个远端触发节点，128，调用 100，四种策略，采集开关 | 24 |
| non-monotonic | 允许 128/65/32 个节点，调用 100，四种策略，采集开关 | 24 |
| modules | 链图 128，每 16 节点显式标一个模块，调用 100，四种策略，采集开关 | 24 |
| no-cache | 阈值链图 32，关闭三类缓存，调用 100，四种策略，采集开关 | 24 |

表中耗时为开启采集时缩减墙钟的三次中位数，不含 Python 启动与模型生成。
判定次数包含强制初检和最终复检，因此 100 次候选预算对应最多 102 次实际判定。
同样调用预算下，采集开关和重复运行的有序候选、调度轨迹与结果检查全部通过。
时间预算只比较质量，不要求轨迹相同。

完整命令、批次路径、环境、源码 SHA-256、汇总和兼容性记录见
[证据摘要](performance-batch4-evidence.json)。所有 468 份产物的实际字节摘要与报告一致，
读回校验和绕过缓存的最终故障复检通过；每个批次的源码摘要都与当前实现一致。

对 legacy 的配对比较中，每种其他策略各 117 对。staged-fast、staged-complete 均为
111 对成本持平、6 对改善；stateful 为 105 对持平、6 对改善、6 对退化。
这些包含三次重复与采集开关，**不是 117 个独立模型**，也不表示一般场景无质量退化。
完整成本仍按 `(nodes, bytes, outputs, inputs, initializers)` 字典序比较。
fast 的成本即使相同，也始终只报告最小性未证明。

## 常规输入：仍有调度开销

规模 128 的两种预算及规模 512 的调用预算下，五类输入的最终完整成本与内容摘要均相同。
以下为规模 512、候选预算 100 的结果；除 fast 外均完成固定点覆盖。

| 场景 | legacy / stateful / fast / complete 耗时（ms） | 实际判定四策略 | 共同最终成本 |
| --- | --- | --- | --- |
| initializers | 17.26 / 17.74 / 17.72 / 18.51 | 4 / 4 / 4 / 4 | `(1, 72, 1, 1, 0)` |
| chain | 111.55 / 104.83 / 114.59 / 116.09 | 21 / 15 / 21 / 21 | `(1, 111, 1, 2, 0)` |
| branches | 144.74 / 125.16 / 145.61 / 146.49 | 23 / 13 / 23 / 23 | `(1, 116, 1, 2, 0)` |
| outputs | 64.21 / 66.50 / 65.64 / 67.47 | 7 / 7 / 7 / 7 | `(1, 127, 1, 2, 0)` |
| missing-shape | 127.69 / 113.65 / 129.92 / 134.46 | 21 / 15 / 21 / 21 | `(1, 99, 1, 2, 0)` |

新阶段切换、收尾枚举和证据仍有成本。当前 coarse 的接受后重新生成规则没有继承
stateful 在这些样本上的判定减少收益；不能把架构拆分本身当成性能改善。
新加入的读回校验应用于全部策略，表中没有混用旧版、缺少读回校验的耗时作为对照。

## 第三批退化样本复测

### 紧预算的资源清理

32 节点链图、中间 Relu、4 次候选判定配额：

| 策略 | 最终成本 | 实际判定 | 耗时（ms） |
| --- | --- | ---: | ---: |
| legacy | `(8, 395, 1, 2, 0)` | 6 | 16.05 |
| stateful | `(8, 412, 1, 3, 0)` | 6 | 16.31 |
| staged-fast | `(8, 395, 1, 2, 0)` | 6 | 16.87 |
| staged-complete | `(8, 395, 1, 2, 0)` | 6 | 16.75 |

有额度限制的 cleanup 修复此样本的多余输入和 17 字节退化。四种运行都因预算停止，
最小性未证明；没有为清理或收尾额外增加候选配额。

### 16/12/6 的尺度恢复

四种策略都得到 `(6, 307, 1, 1, 0)`：

| 策略 | 实际判定 | 耗时（ms） | 最小性 |
| --- | ---: | ---: | --- |
| legacy | 16 | 27.60 | pass_fixed_point |
| stateful | 75 | 130.82 | pass_fixed_point |
| staged-fast | 17 | 31.09 | unproven |
| staged-complete | 23 | 41.83 | pass_fixed_point |

coarse 接受到 12 节点后，按新模型重建尺度，能直接尝试 6 节点粗块。
本次 complete 无需在收尾中接受编辑；完成收尾的额外实际判定为 6 次。
它改善了相对于 stateful 的退化，仍比 legacy 多 7 次判定。
收尾中接受后不返回启发式搜索的规则另由强制收尾回归测试验证。

### 规模阈值仍然退化

128 节点、至少保留 32 节点、100 次候选预算，最终均为 `(32, 1614, 1, 1, 0)`：

| 策略 | 实际判定 | 耗时（ms） | 最小性 |
| --- | ---: | ---: | --- |
| legacy | 68 | 167.17 | pass_fixed_point |
| stateful | 102 | 220.79 | unproven |
| staged-fast | 97 | 223.84 | unproven |
| staged-complete | 102 | 254.25 | unproven |

staged-complete 已进入收尾，但总调用预算阻止其完成；不会隐式扩充预算或声明固定点。
当前区域保留方向依然产生很多失败尝试，这是后续方向排序/阶段额度研究的保留样本。

## 区域、非单调与缓存关闭

跨区域场景均缩至 `(2, 182, 1, 3, 0)`。legacy、stateful、staged-complete 分别为
79 / 44 / 60 次判定，190.01 / 144.19 / 163.92 ms。staged 优于 legacy，仍慢于 stateful。

非单调 128/65/32 条件下，100 次候选预算内 legacy 停在 128 节点，其他三种运行达到
32 节点；complete 为 271.58 ms、102 次总判定，最小性仍未证明。

显式模块链图中，四种策略均得到 `(1, 151, 1, 2, 0)`；complete 为 49.65 ms、17 次判定，
未显示模块加速。此普通单触发图在 coarse 已缩至一个节点；非连续模块组合需要保留整组的
情形另由模块候选接受测试覆盖。这里的显式标注不代表真实导出器模块解析验收。

关闭缓存的 32 节点阈值图均达到 `(8, 401, 1, 1, 0)`；legacy、stateful、complete 分别为
20 / 63 / 60 次判定。complete 的收尾有 27 次实际判定，完整运行为 84.21 ms，
仍显著贵于 legacy 的 33.47 ms。固定点扫描不会因为缓存关闭被省略。

## 正确性与交付验证

- 全量测试 **277 passed**；Ruff 检查、格式检查和差异空白检查通过。
- 60 组 legacy/stateful 修改前后等价对照通过；468 次矩阵的调用预算决策重复性与采集开关对照通过。
- 新增测试覆盖跨区域、阈值、非单调、死节点、缺类型、控制流捕获、模块非连续成员、
  错误标注回退、旧基准失效、收尾接受重扫、去重表淘汰、预算及不确定判定。
- 独立收尾恢复原始签名，另一缺陷不能重新建立基线；命令、超时、正则、模型或工作目录
  不匹配时，在后端调用前拒绝。
- 教学 Relu 示例完成 fast → 独立 complete 的 CLI 流程，实际交付文件通过严格 ONNX 校验，
  保留 DEMO_RELU 身份，最终实际路径判定未命中缓存。产物及命令见证据摘要的 `cli`。

这些结果支持保留实验入口，尚未验证真实后端故障，也没有普遍性能改善的结论。
