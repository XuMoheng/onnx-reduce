# 活跃子图缩减

本轮解决一个实际搜索缺口：保留节点却沿用旧图输出时，故障算子会变成无用节点。
后端若在编译前裁掉无用节点，候选就会失败；逐个旁路尾部节点仍可能可行，但每次接受前
重新扫描大批失败的删除候选，容易在预算内留下数百节点。

新候选 `ExtractNodes` 同时提取节点、重建其真实输入输出并裁掉无关资源，接受条件仍为
成本严格下降、原校验策略通过、同一目标故障复现。默认先尝试最多 16 个快速片段，
避免新策略独占预算，后面的完整提取 pass 还会覆盖每个主图单节点。
代表节点和拓扑分区交替生成，避免算子类型很多时只顾逐一探测。

## 可复现的 1500 节点对照

基线为 `ea6820e`，即本轮修改前版本。构造 1500 个节点的链，第 1140 个节点为故障载体；
判定器从实际图输出反向遍历，只接受仍活跃的载体，模拟后端裁掉无用节点的行为。
这不是内网故障模型，也不是真实编译器缺陷的证据。

三个场景均使用实际 ONNX 候选文件和独立最终复检：

- `live_op`：链中有一个活跃 Relu，其他为 Identity；暴露原有的输出边界问题。
- `live_name`：所有节点都是 Relu，但只有特定的活跃节点是故障载体，检查策略不依赖稀有算子提示。
- `locked`：全部 1500 个节点必须活跃；检查策略在无法继续缩减时的成本。

固定候选调用预算为 128 次；另测 1 秒软时间预算。三种调度器、每项重复 3 次，共 54 组对照、
108 次独立运行，交替两侧执行顺序，同一 Python 解释器、依赖和判定条件，开启 performance 和缓存，
编辑模式为默认 IR。模型构造和 Python 导入不计入缩减计时。

```bash
mkdir -p /tmp/onnx-reduce-before-fragments
git archive ea6820e | tar -x -C /tmp/onnx-reduce-before-fragments
.venv/bin/python benchmarks/live_fragments.py \
  --baseline-source /tmp/onnx-reduce-before-fragments \
  --current-source /path/to/initial-fragment-source \
  --cases live_op,live_name,locked --out output/live-fragments-ir --repeat 3 \
  --candidate-budget 128 --time-budget 1
```

可用 `--model-edit-mode auto`、`--cases live_name`、`--schedulers staged` 单独对照。
测量应串行执行，避免同时跑测试或其他负载。

## 第一轮测量（加入接口变体前）

以下均为 3 次运行中位数，调用数含强制初检和最终复检。耗时以秒计，限本机模拟负载。

| 场景 | 调度器 | 128 次候选预算的最终节点数（旧→新） | 判定调用数（旧→新） | 缩减耗时（旧→新） |
|---|---|---:|---:|---:|
| live_op | legacy | 364→1 | 130→5 | 1.877→0.058 |
| live_op | stateful | 345→1 | 130→5 | 2.624→0.059 |
| live_op | staged | 353→1 | 130→5 | 2.272→0.062 |
| live_name | legacy | 364→1 | 130→22 | 1.924→0.227 |
| live_name | stateful | 345→1 | 130→44 | 2.623→0.503 |
| live_name | staged | 353→1 | 130→28 | 2.263→0.301 |
| locked | legacy | 1500→1500 | 130→130 | 7.482→6.852 |
| locked | stateful | 1500→1500 | 130→130 | 11.902→10.183 |
| locked | staged | 1500→1500 | 130→130 | 11.201→3.370 |

在 1 秒软预算下，live_op/live_name 的新结果也均为 1 节点，旧结果为 357–372 节点；
locked 两侧均保留全部节点。锁定场景在相同时间预算下，新版完成的实际判定更多。
时间限制允许当前准备/判定及最终复检越界，因此总耗时不应与 1 秒严格相等。

这些故障条件明确要求至少一个活跃节点，因此得到 1 节点就达到了它们的节点数下界。
该结论仅针对这两个构造条件。普通 `pass_fixed_point` 仍只描述配置候选集合上的固定点，
不能证明任意故障的全局最小。

[证据摘要](live-fragments-results.json) 记录环境、源码摘要、全部样本的最终成本、判定数、停止原因和时间。
原始 report.json、候选、接受记录及实际产物位于 Git 忽略的 output/live-fragments-ir-v2/。

Python 3.11、3.12、3.13 各 465 项测试通过，3.11 源码分发包的 465 项测试也通过。
实际安装的 wheel 独立验证同样将构造模型从 1500 节点缩到 1 节点，共 5 次判定并通过最终复检。

## 第二轮：输出投影与固定接口

第一轮默认暴露保留节点的全部输出，且可能把图输入名改成切割处的中间值名。
新的回归验证这两种条件会拒绝合法的一节点复现：判定器只处理某个 Split 输出，或继续
要求原输入输出名字。现在每个单节点也尝试单输出投影，以及保留原接口的变体。

接口保持不增加额外节点，严格匹配类型和 shape，保留名字、顺序、未使用输入及必要默认权重。
作用域改名会拒绝冲突和捕获遮蔽；每个候选仍须通过相同的 checker、成本和故障身份判断。
普通粗分区及奇数尾块优先执行，之后才尝试延后的接口变体，避免重复的无效接口探测拖慢二分搜索。

性能对照基线是第一轮的源码快照（其摘要见第一轮证据），对应已构建的 0.1.0 源码分发包。
第二轮额外加入 fixed_io 和 project_output 两种 1500 节点场景，判定条件仅增加接口/输出约束。
默认 legacy 的五个场景各测调用预算和时间预算、重复 3 次；stateful/staged 的新场景另作单次检查。
[第二轮证据](interface-fragments-results.json) 保存具体配置、样本、环境及源码摘要。

| legacy 场景 | 第一轮→第二轮节点数 | 第一轮→第二轮判定次数 | 第一轮→第二轮耗时（秒） |
|---|---:|---:|---:|
| live_op | 1→1 | 5→5 | 0.059→0.059 |
| live_name | 1→1 | 22→22 | 0.221→0.221 |
| fixed_io | 1500→1 | 130→6 | 6.972→0.066 |
| project_output | 364→1 | 130→10 | 1.985→0.082 |
| locked | 1500→1500 | 130→130 | 7.026→7.170 |

表中为固定调用预算的 3 次中位数，判定次数包含首尾检查。1 秒时间预算下，两个新场景的
第二轮结果也均为 1 节点；stateful/staged 的两个新场景在两种预算下的单次检查均为 1 节点。
locked 的本次耗时约增加 2%，其他负载的结果不保证相同，不能将此表当成真实后端速度保证。
候选顺序优化前 live_name 曾增加到 33 次判定；将普通分区的奇数尾块纳入优先轮次后恢复为 22 次。

Python 3.11、3.12、3.13 上各 478 项测试通过，3.11 源码分发包也通过全部 478 项测试。
实际安装的第二轮 wheel 另行验证 fixed_io/project_output，均达到 1 节点，分别为 6/10 次判定。

复现时保留两个源码目录；第一轮基线是本轮改动前的源包或源码，而非 ea6820e：

```bash
.venv/bin/python benchmarks/live_fragments.py \
  --baseline-source /path/to/before-interface-variants \
  --current-source "$PWD" --schedulers legacy \
  --out output/interface-comparison --repeat 3 --time-budget 1
```
